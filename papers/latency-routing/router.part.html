All four instances are given identical service capacity here, so every latency difference on screen comes from routing alone rather than from one model being faster. Prompt and response lengths are representative of the four tasks — short/long in each direction — rather than their measured distributions, and are scaled so the paper's TTFT targets are reachable on an idle instance. Accuracy comes from the paper's LLM-as-a-judge scores and cost from published Qwen3 per-token prices, so the utility each router chases is the real one — which is why Qwen3-0.6B is never the utility-maximising choice for any of the four tasks, and an accuracy–cost router leaves it idle while the instances it prefers saturate. The engine here is a token-batch simulator, and SFS is that same simulator rolled forward from each instance's current workload using predicted decode lengths (±30% error), so it is close to exact by construction. The paper's evidence that this holds against a real vLLM deployment is the 5% TTFT error measured below.
